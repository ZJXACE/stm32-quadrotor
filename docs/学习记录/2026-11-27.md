## 一、知识点：为什么消抖要用 `vTaskDelay`，不能用 `HAL_Delay`

`HAL_Delay(5)` 在 HAL 里的实现是**忙等系统节拍**：

```c
while ((HAL_GetTick() - tickstart) < wait) { }   /* 空转 5ms */
```

在 FreeRTOS 里，这 5ms 是**占着 CPU 空转**的——低优先级任务（LED、电源）全被饿住，时间还照样浪费。

`vTaskDelay(5)` 是**让出 CPU**：把任务挂到延时列表，调度器立刻切给别的任务，1ms 后再回来。

| 场景 | 用什么 |
| --- | --- |
| 调度器**还没启动**（`main` 里的 `HAL_Delay(200)`） | `HAL_Delay` |
| 任务里（调度器已启动） | **`vTaskDelay`** |
| 中断里 | 都不能用！用 `xTaskGetTickCountFromISR` / 打标记 |

> 判断依据只有一条：**当前在不在任务上下文里**。

## 二、知识点：电平触发 vs 边沿触发

如果按键函数在"检测到按下"时立刻返回：

```c
if (按下) return KEY_UP;      /* ❌ 电平触发 */
```

假设任务 10ms 扫一次，你按了 300ms → 这 30 次扫描**每次都返回 KEY_UP** → 菜单翻 30 页。

正确做法是**等抬起再返回**（只在"按下→抬起"这个动作结束时返回一次）：

```c
while (仍然按下);      /* 等松开 */
return KEY_UP;         /* 一次按键 = 一次返回 */
```

代价：**快速连按时，上一次没抬起就不会检测下一个键**；对遥控器这种场景可以接受（人不可能同时按两个键）。

想同时支持"按住连发"（比如音量键），就要另外做**重复触发计时**：按下后每 100ms 触发一次，而不是靠 `while` 死等。

## 三、知识点：长按 = 两个时间点相减

```c
TickType_t t1 = xTaskGetTickCount();   /* 按下瞬间 */
/* ...等抬起... */
TickType_t t2 = xTaskGetTickCount();   /* 抬起瞬间 */
if (t2 - t1 > pdMS_TO_TICKS(1000)) { 长按 }
```

三条规矩：

**① 一定用减法，不要用"加法后比较"**

```c
if (now > t1 + 1000)      /* ❌ tick 溢出后就永远不成立 */
if (now - t1 > 1000)      /* ✅ 无符号减法，溢出也正确 */
```

32 位 tick @1000Hz，**49.7 天**翻一次；减法在溢出点依然给出正确差值（模 2^32 运算）。

**② 用 `pdMS_TO_TICKS()` 而不是裸数字**

你现在 `configTICK_RATE_HZ = 1000`，1 tick = 1ms，所以 `1000` 恰好等于 1 秒。**但换工程/改节拍率时它就错了**，而 `pdMS_TO_TICKS(1000)` 永远对。

**③ 等待期间要"让 CPU"**

```c
while (仍然按下) { vTaskDelay(1); }    /* ✅ 每 1ms 让一次 */
while (仍然按下);                       /* ❌ 纯死等，低优先级任务全饿死 */
```

## 四、知识点：`else if` 是"就近匹配"的

```c
if (A) { ... }
else if (B) { ... }     /* 属于哪个 if？→ 最近的、还没配对的 if */
```

正因为"就近匹配"，**少写一个 `}` 不会报错**：编译器会把它当成"内层 if 的 else"，语法上完全合法。

判断方法（不用编译器）：

> **数花括号深度**。函数体应该是 1；每个 `if`/`else if` 的块进出一次，深度应该回到 1。
> 如果某个 `else if` 的深度是 2，说明它被套进了上一个分支里 —— 那个分支就成了"它的前置条件"。

## 六、方法论：这次是怎么定位的

1. **先缩小范围**："1~4 正常、5/6/8 不正常" —— 说明**前半段代码是对的**，问题在链的后半段；
2. **怀疑顺序**：按键驱动常见故障依次是"引脚没配对 → 上拉/电平极性反了 → 消抖 → 逻辑分支不可达"；
3. **看结构不看语法**：编译 0 Error 也可能逻辑错，所以用"花括号深度"这种**结构指标**去查；
4. **一次只改一个变量**：补 `}` 后先只测按键 5，再测 6/8，避免一次改多处又说不清哪处生效。

> 这条经验可以推广：**"部分功能正常、另一部分完全不响应"时，优先怀疑控制流的挂接位置（`if/else` 链、`switch` 的 `break`、循环的 `continue`），而不是硬件。**

## 八、晚上补充：定义、声明、链接 —— C 的"文件边界"

> 这一段是今天傍晚写 `remote` 数据通路时踩出来的，属于**C 语言里最容易被忽略、但工程里天天用**的知识。

### 1. 三个词，一件事

| 概念 | 写法 | 放哪 | 数量 | 干什么 |
| --- | --- | --- | --- | --- |
| **定义** | `Remote_Data remote = {0};` | `.c` | **全工程只能 1 份** | 真正分配内存 |
| **声明** | `extern Remote_Data remote;` | `.h` | 可以很多份 | 只告诉编译器"有这么个东西" |
| **使用** | `remote.Shutdown = 1;` | 任意 `.c` | — | 前提：include 过头文件 |

口诀：**「分配内存的叫定义（.c），只报名不分配的叫声明（.h + extern）」**

### 2. 为什么必须有 extern：编译是"一个文件一个文件"来的

```
① 编译：每个 .c 单独变成一个 .o
   APP_process_data.c  ──编译──►  APP_process_data.o   （remote 的内存在这里）
   APP_freertos_task.c ──编译──►  APP_freertos_task.o  （只知道"我要用 remote"）

② 链接：把 .o 拼起来，把"名字"换成"地址"
   链接器：谁定义了 remote？→ APP_process_data.o ✅ → 填上地址

③ 输出 .axf / .hex
```

**关键**：编译 `APP_freertos_task.c` 时，编译器**看不到** `APP_process_data.c` 的内容。它只认「当前 .c + 它 include 的 .h」。

所以必须在 `.h` 里写 `extern`，等于告诉它：

> "有这么个变量，类型是 `Remote_Data`，内存别人已经分配好了，你尽管用名字，链接时能对上。"

### 3. 今天踩的 4 个坑（都是同一类知识的不同角度）

| # | 报错原文 | 原因 | 解决 |
| --- | --- | --- | --- |
| 1 | `未定义标识符 key_pitch_offset` | 变量定义在 `APP_process_data.c`，但头文件**没有 extern 声明** | 头文件加 `extern int16_t key_pitch_offset;` |
| 2 | `declaration is incompatible with "uint16_t key_roll_offset"` (147) | `.h` 写 `uint16_t`，`.c` 写 `int16_t`，**类型不一致** | 统一成 `int16_t`（微调量有正负） |
| 3 | `L6218E: Undefined symbol Shutdown` | 给**结构体成员**写了 `extern uint8_t Shutdown;` —— 成员不是独立变量，全工程没有它的定义 | 删掉，改用 `remote.Shutdown` |
| 4 | `identifier "Remote_Data" is undefined` | `extern Remote_Data remote;` 写在**结构体定义之前**，C 从上往下读，那时还不认识这个类型 | 挪到 `}Remote_Data;` 之后 |

### 4. 头文件的正确排版顺序

```c
#ifndef __APP_PROCESS_DATA_H__
#define __APP_PROCESS_DATA_H__

/* ① 先 include 依赖（类型来源） */
#include "main.h"

/* ② 再定义类型（struct / enum / typedef） */
typedef struct { ... } Remote_Data;

/* ③ 再声明全局变量（extern）—— 必须在类型定义之后！ */
extern Remote_Data remote;
extern int16_t key_pitch_offset;

/* ④ 最后声明函数 */
void App_Process_KeyData(void);

#endif
```

**原因**：C 是**单遍扫描、从上往下**。任何"用到某个类型"的语句，都必须写在该类型定义之后。

### 5. 编译错误 vs 链接错误（判断故障阶段）

| 阶段 | 典型报错 | 说明 |
| --- | --- | --- |
| 预编译 | 找不到头文件 `cannot open source input file` | 路径/文件名 |
| 编译 | `未定义标识符`、`不兼容的声明`、`语法错误` | 类型/名字/语法 |
| **链接** | `L6218E: Undefined symbol xxx` | **声明了但没有定义**（或忘了把 .c 加进工程） |
| 链接 | `L6200E: Symbol xxx multiply defined` | 定义了两份 |

**记忆点**：能编译过但链接失败 = "名字有，实体没有"。

### 6. 有符号还是无符号：这次必须 `int16_t`

```c
uint16_t key_roll_offset;
key_roll_offset -= 10;    /* 在 0 附近：0 - 10 = 65526 ← 下溢！ */
```

| 用途 | 类型 | 打印格式 |
| --- | --- | --- |
| 微调量（可正可负） | **`int16_t`** | `%d` |
| ADC 原始值、计数（只增） | `uint16_t` | `%u` |

**微调量、PID 误差、坐标偏移这类"会变负"的量，一律用有符号类型。**

### 7. 一段能直接复用的"数据通路"模板

```c
/* ---------- xxx.h ---------- */
typedef struct { uint16_t a; uint8_t b; } Xxx_Data;
extern Xxx_Data xxx;              /* 结构体定义之后 */
extern int16_t xxx_offset;

/* ---------- xxx.c ---------- */
#include "xxx.h"
Xxx_Data xxx = {0};               /* 全局唯一的定义 */
int16_t xxx_offset = 0;

/* ---------- 其他 .c ---------- */
#include "xxx.h"
xxx.b = 1;                        /* 直接改，多个任务共享 */
```

这就是今天的 `remote` 结构体：**按键任务写它 → 发送任务读它 → 打包发出去**。多任务共享数据时，结构体 + `extern` 是最常用的方法（进阶再上队列/互斥锁）。

### 8. 一句话总结

> **`.c` 里定义（一份）、`.h` 里 `extern` 声明（可多份）、类型必须先定义后使用、结构体成员不能单独 extern。**
