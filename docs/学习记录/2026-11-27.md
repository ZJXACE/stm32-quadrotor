## 一、知识点：为什么消抖要用 `vTaskDelay`，不能用 `HAL_Delay`

`HAL_Delay(5)` 在 HAL 里的实现是**忙等系统节拍**：

```c
while ((HAL_GetTick() - tickstart) < wait) { }   /* 空转 5ms */
```

在 FreeRTOS 里，这 5ms 是**占着 CPU 空转**的——低优先级任务（LED、电源）全被饿住，时间还照样浪费。

`vTaskDelay(5)` 是**让出 CPU**：把任务挂到延时列表，调度器立刻切给别的任务，1ms 后再回来。

| 场景 | 用什么 |
| --- | --- |
| 调度器**还没启动**（`main` 里的 `HAL_Delay(200)`） | `HAL_Delay` |
| 任务里（调度器已启动） | **`vTaskDelay`** |
| 中断里 | 都不能用！用 `xTaskGetTickCountFromISR` / 打标记 |

> 判断依据只有一条：**当前在不在任务上下文里**。

## 二、知识点：电平触发 vs 边沿触发

如果按键函数在"检测到按下"时立刻返回：

```c
if (按下) return KEY_UP;      /* ❌ 电平触发 */
```

假设任务 10ms 扫一次，你按了 300ms → 这 30 次扫描**每次都返回 KEY_UP** → 菜单翻 30 页。

正确做法是**等抬起再返回**（只在"按下→抬起"这个动作结束时返回一次）：

```c
while (仍然按下);      /* 等松开 */
return KEY_UP;         /* 一次按键 = 一次返回 */
```

代价：**快速连按时，上一次没抬起就不会检测下一个键**；对遥控器这种场景可以接受（人不可能同时按两个键）。

想同时支持"按住连发"（比如音量键），就要另外做**重复触发计时**：按下后每 100ms 触发一次，而不是靠 `while` 死等。

## 三、知识点：长按 = 两个时间点相减

```c
TickType_t t1 = xTaskGetTickCount();   /* 按下瞬间 */
/* ...等抬起... */
TickType_t t2 = xTaskGetTickCount();   /* 抬起瞬间 */
if (t2 - t1 > pdMS_TO_TICKS(1000)) { 长按 }
```

三条规矩：

**① 一定用减法，不要用"加法后比较"**

```c
if (now > t1 + 1000)      /* ❌ tick 溢出后就永远不成立 */
if (now - t1 > 1000)      /* ✅ 无符号减法，溢出也正确 */
```

32 位 tick @1000Hz，**49.7 天**翻一次；减法在溢出点依然给出正确差值（模 2^32 运算）。

**② 用 `pdMS_TO_TICKS()` 而不是裸数字**

你现在 `configTICK_RATE_HZ = 1000`，1 tick = 1ms，所以 `1000` 恰好等于 1 秒。**但换工程/改节拍率时它就错了**，而 `pdMS_TO_TICKS(1000)` 永远对。

**③ 等待期间要"让 CPU"**

```c
while (仍然按下) { vTaskDelay(1); }    /* ✅ 每 1ms 让一次 */
while (仍然按下);                       /* ❌ 纯死等，低优先级任务全饿死 */
```

## 四、知识点：`else if` 是"就近匹配"的

```c
if (A) { ... }
else if (B) { ... }     /* 属于哪个 if？→ 最近的、还没配对的 if */
```

正因为"就近匹配"，**少写一个 `}` 不会报错**：编译器会把它当成"内层 if 的 else"，语法上完全合法。

判断方法（不用编译器）：

> **数花括号深度**。函数体应该是 1；每个 `if`/`else if` 的块进出一次，深度应该回到 1。
> 如果某个 `else if` 的深度是 2，说明它被套进了上一个分支里 —— 那个分支就成了"它的前置条件"。

## 五、踩坑记录（现象 / 原因 / 解决）

| # | 现象 | 原因 | 解决 |
| --- | --- | --- | --- |
| 1 | 按键 5、6、8 按了没反应，1~4 正常 | `KEY_RIGHT` 分支少一个 `}`，导致 `KEY_LEFT_X`/`KEY_RIGHT_X` 成了"内层 `if` 的 `else`"，只有按住右方向键才会被检查 | 补 `}` + 删末尾多余的 `}`；用花括号深度逐行核对 |
| 2 | 一次按键会打印很多次 | "检测到按下就 return"是**电平触发** | 改成"等抬起再 return"（边沿触发） |
| 3 | 长按判定不准/偶尔失效 | 用 `now > t1 + 1000` 比较，tick 溢出后失效；且直接写 1000 依赖节拍率 | 改成 `now - t1 >= pdMS_TO_TICKS(1000)` |
| 4 | 按键任务里用 `HAL_Delay` 消抖 | RTOS 任务上下文里 `HAL_Delay` 是忙等，饿死其他任务 | 换 `vTaskDelay` |
| 5 | 枚举值跳到 8（没有 7） | 中途删过枚举项 | 保持连续编号，或者至少注释说明为什么跳号 |

## 六、方法论：这次是怎么定位的

1. **先缩小范围**："1~4 正常、5/6/8 不正常" —— 说明**前半段代码是对的**，问题在链的后半段；
2. **怀疑顺序**：按键驱动常见故障依次是"引脚没配对 → 上拉/电平极性反了 → 消抖 → 逻辑分支不可达"；
3. **看结构不看语法**：编译 0 Error 也可能逻辑错，所以用"花括号深度"这种**结构指标**去查；
4. **一次只改一个变量**：补 `}` 后先只测按键 5，再测 6/8，避免一次改多处又说不清哪处生效。

> 这条经验可以推广：**"部分功能正常、另一部分完全不响应"时，优先怀疑控制流的挂接位置（`if/else` 链、`switch` 的 `break`、循环的 `continue`），而不是硬件。**
