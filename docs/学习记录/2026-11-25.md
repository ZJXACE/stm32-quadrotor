# 2026-11-25 · 把四个 LED 做成一套"状态指示灯"

## 一、今天的思路是怎么一步步长出来的

这是今天最该记住的部分——**代码不是一次写成的，是四次抽象叠上去的**。

### 第 1 步：先让一个灯能亮（能跑就行）

CubeMX 里把四个引脚配成推挽输出、初始高电平，然后在任务里直接写：

```c
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_12, GPIO_PIN_RESET);   // 点亮 LED1
```

能亮。但这样写四盏灯，就要写四行，还要记住四个引脚——**引脚号是"知识"，不该散落在代码里**。

### 第 2 步：把"一盏灯"变成一个对象

```c
typedef struct
{
    GPIO_TypeDef *GPIOx;   // 哪个端口
    uint16_t      Pin;     // 哪个引脚
} Led_Struct;
```

```c
Led_Struct LEFT_TOP_LED = { .GPIOx = LED1_GPIO_Port, .Pin = LED1_Pin };
```

从此函数只认"灯"，不认引脚：

```c
void Int_led_on(Led_Struct *led) { HAL_GPIO_WritePin(led->GPIOx, led->Pin, GPIO_PIN_RESET); }
```

**这就是面向对象的雏形**：把一组固定参数打包成一个概念，调用方只关心"操作哪盏灯"。
以后加第 5 颗灯，只需要加一行结构体，四个函数一行都不用改。

### 第 3 步：意识到"灯不是随便闪的，它要表达状态"

写到这里才想明白：无人机上的灯不是装饰，是**给人看的状态显示**。

- 前面两个灯（PA12/PA11）→ 告诉操作者：**遥控器连上了没有**
- 后面两个灯（PB15/PB14）→ 告诉操作者：**飞机现在在干什么**

于是问题从"怎么让灯闪"变成了"**怎么让代码里的状态准确地显示出来**"。这是今天最重要的思维转变。

### 第 4 步：用枚举把"状态"变成代码

`Common/Com_config.h`：

```c
typedef enum { REMOTE_CONTROL_CONNECTED = 0, REMOTE_CONTROL_DISCONNECTED = 1 } RemoteControl_Status;
typedef enum { IDLE = 0, FLIGHT = 1, Fix_Height = 2, Error = 3 } Plane_Status;
```

为什么不直接用 `0 / 1 / 2 / 3`？

| 写法 | 三个月后的你看到 |
| --- | --- |
| `if (plane_state == 2)` | "2 是什么意思？" |
| `if (plane_state == Fix_Height)` | 一眼就懂 |

**枚举是"给数字起名字"，也是给自己留说明书。**

## 二、数据结构全景

```
Led_Struct          → 一盏灯（端口 + 引脚）
RemoteControl_Status → 遥控器状态（2 个值）
Plane_Status         → 飞行状态（4 个值）
```

四个灯对象 + 两个全局状态变量，就构成了整个指示系统的"数据层"：

```c
Led_Struct LEFT_TOP_LED   = { LED1_GPIO_Port, LED1_Pin };        // PA12
Led_Struct RIGHT_TOP_LED  = { LED2_GPIO_Port, LED2_Pin };        // PA11
Led_Struct RIGHT_BOTTOM_LED = { LED3_GPIO_Port, LED3_Pin };      // PB15
Led_Struct LEFT_BOTTOM_LED  = { LED4_GPIO_Port, LED4_Pin };      // PB14

RemoteControl_Status remote_control_status = REMOTE_CONTROL_CONNECTED;
Plane_Status         plane_state           = Error;
```

## 三、控制流：一个 100ms 节拍 + 取余做"软件分频"

`Int_Led_Task` 每 100ms 醒一次，一次管四盏灯：

| 状态 | 灯效 | 代码 | 实际周期 |
| --- | --- | --- | --- |
| 遥控已连接 | 前两灯常亮 | `Int_led_on()` 每次调用 | — |
| 遥控断开 | 前两灯熄灭 | `Int_led_off()` | — |
| `IDLE` 空闲 | 后两灯慢闪 | `if (Count % 5 == 0) toggle` | 5 × 100ms = **500ms** |
| `FLIGHT` 飞行 | 后两灯快闪 | `if (Count % 2 == 0) toggle` | 2 × 100ms = **200ms** |
| `Fix_Height` 定高 | 后两灯常亮 | `Int_led_on()` | — |
| `Error` 故障 | 后两灯熄灭 | `Int_led_off()` | — |

**为什么不用 `vTaskDelay(500)` 做慢闪？**
因为一个任务要同时管四盏灯，如果每盏灯各用一个 `vTaskDelay`，任务就被"锁死"在某盏灯上了。
用**统一节拍 + 取余**，等于给每个灯单独算一个"分频系数"——这就是嵌入式中最常用的**软件分频/时间片**思路。

```c
Count++;                                  // 每 100ms 加 1
if (Count % 5 == 0)  toggle(慢闪灯);       // 每 5 拍 = 500ms
if (Count % 2 == 0)  toggle(快闪灯);       // 每 2 拍 = 200ms
if (Count == 10) Count = 0;               // 1 秒一个循环，防止无限增大
```

## 四、关键代码（带解释）

```c
void Int_Led_Task(void *pvParameters)
{
    uint8_t Count = 0;
    portTickType lastWakeTime = xTaskGetTickCount();
    while (1)
    {
        Count++;

        // ---- 前两个灯：表达"遥控器连没连上" ----
        if(remote_control_status == REMOTE_CONTROL_CONNECTED)
        {
            Int_led_on(&LEFT_TOP_LED);
            Int_led_on(&RIGHT_TOP_LED);
        }
        else
        {
            Int_led_off(&LEFT_TOP_LED);
            Int_led_off(&RIGHT_TOP_LED);
        }

        // ---- 后两个灯：表达"飞控在什么状态" ----
        if(plane_state == IDLE)                    // 空闲：慢闪 500ms
        {
            if(Count % 5 == 0) { Int_led_toggle(&LEFT_BOTTOM_LED); Int_led_toggle(&RIGHT_BOTTOM_LED); }
        }
        else if(plane_state == FLIGHT)             // 飞行：快闪 200ms
        {
            if(Count % 2 == 0) { Int_led_toggle(&LEFT_BOTTOM_LED); Int_led_toggle(&RIGHT_BOTTOM_LED); }
        }
        else if(plane_state == Fix_Height)         // 定高：常亮
        {
            Int_led_on(&LEFT_BOTTOM_LED); Int_led_on(&RIGHT_BOTTOM_LED);
        }
        else if(plane_state == Error)              // 故障：熄灭
        {
            Int_led_off(&LEFT_BOTTOM_LED); Int_led_off(&RIGHT_BOTTOM_LED);
        }

        if(Count == 10) Count = 0;
        vTaskDelayUntil(&lastWakeTime, LED_task_period);   // 100ms
    }
}
```

逐段说明：

1. `Count` 是"第几拍"，整个函数的时间感都建立在它上面
2. `vTaskDelayUntil` 而不是 `vTaskDelay`：保证 100ms 是**严格**的，不会因为任务执行时间累积误差
3. `Int_led_off` 写在 else 里，而不是"只在状态变化时写一次"——因为每 100ms 重写一次是幂等的，简单可靠，不用额外记"上次状态"
4. 最后 `Count == 10` 归零：既防止 `uint8_t` 溢出，也让"1 秒"成为一个完整循环

## 五、学习感悟

### 1. 优先级 1 = "地基"思维

![灯的优先级为什么给 1](../../2_%E7%AC%94%E8%AE%B0/11%E6%9C%8825%E6%97%A5/Snipastex_2026-11-24_19-39-31.png)

截图里这句话是今天最有价值的思考：

> 灯的运行优先级调最低：1（比空闲任务还是大一点点的）。就像地基，如果地基都没问题、任务正常运行，那么其它任务也没有问题。

**为什么灯要最低优先级？** 因为灯是"给人看的"，晚 10ms 亮起来没人会死；但电机控制晚 1ms，飞机就偏了。
反过来，**灯能正常按节奏闪，说明调度器在正常切任务、系统没卡死**——这就是最便宜的"系统健康指示灯"。

### 2. 先想"要表达什么"，再想"怎么实现"

如果一上来就写"怎么让灯闪"，最后大概率写成一堆 `vTaskDelay(500)`；先想清楚"灯要表达两个状态"，结构自然就分成了两组、两个数据源。

### 3. 枚举 > 魔法数字

状态值用枚举，`if (plane_state == Fix_Height)` 比 `if (plane_state == 2)` 可读一个数量级。而且以后加状态（比如 `LANDING`），只要在枚举里加一行。

### 4. 结构体 = 把散落的参数收成一个概念

`Led_Struct` 只有两个成员，但它把"哪盏灯"这件事从调用方转移到了定义处——**调用方越少知道细节，代码越不容易错**。

### 5. 一个任务管多件事 → 统一节拍 + 分频

这是嵌入式的通用套路：定时器 / 任务给一个"最小时间片"，各功能用"计数取余"得到自己的节奏。比"一个功能一个任务"省 RAM（这个项目只有 20KB），也比"一个功能一个软件延时"可靠。

## 六、踩的坑

| # | 现象 | 原因 | 解决 |
| --- | --- | --- | --- |
| 1 | 两个灯死活不亮 | `remote_control_status` 初值是 `DISCONNECTED`，而全工程**没有任何地方**把它改成 `CONNECTED` → 每次都进 else 熄灭 | 调试期先写死成 `CONNECTED`；正式版要由遥控通信任务写入 |
| 2 | 后两个灯一直是灭的，以为坏了 | `plane_state` 初值是 `Error`，`Error` 分支就是熄灭 | 想看上电灯效，把初值改成 `IDLE` |
| 3 | `if / else if` 链没有兜底 | 四个分支没有 `else`，如果 `plane_state` 是枚举外的值，灯效会保持上一次，很难查 | 末尾加 `else { 全部熄灭 + Debug_Printf }` |
| 4 | `Count` 手动归零在 10 | 如果以后把任务周期改成 50ms，慢闪就从 500ms 变成 250ms，容易忘 | 归零值、取余值都跟"100ms 节拍"强耦合，改周期时要一起检查 |
| 5 | （昨天的教训）LED 对象指向 PA0 | PA0 在工程里没配置成输出，写它没反应也不报错 | **宏定义才是唯一事实来源**，用 `LED1_Pin` 而不是手写引脚号 |

## 八、补充：Si24R1 与"怎么读手册"

晚上接了 2.4G 模块，顺手把"读手册"这件事练了一遍，记几条以后能复用的。

### 1. 今天真正想通的三个点

**① CSN 和 CE 是两件事，别混**

| 信号 | 管什么 | 类比 |
| --- | --- | --- |
| CSN | **SPI 通信**的开关（低 = 我跟你说话） | 打电话拨通/挂断 |
| CE | **射频收发**的开关（高 = 开始收/发） | 对讲机按下说话键 |

所以：`CSN` 管"能不能跟芯片对话"，`CE` 管"芯片要不要上天线"。两者完全独立。

**② 写寄存器必须加 `0x20`，读不用**

- 读命令 = 地址本身（`0x00~0x1F`）
- 写命令 = 地址 `| 0x20`（`0x20~0x3F`）
- FIFO 命令（`0x61/0xA0/0xE1`）是独立编号，不加 `0x20`

我今天就踩了这个坑：`Int_SI24R1_Write_Reg(STATUS, state)` —— 少加 `0x20`，芯片把 `0x07` 当成"读"，**标志永远清不掉**。编译不报错，只有对手册才发现。

**③ Si24R1 的 STATUS 和 nRF24L01 差一位（重要！）**

| 位 | Si24R1 | nRF24L01+ |
| --- | --- | --- |
| RX_DR | **0x40** | 0x80 |
| TX_DS | **0x20** | 0x40 |
| MAX_RT | **0x10** | 0x20 |

因为 Si24R1 把 bit7 留空了。网上抄 nRF24 的代码套到 Si24R1 上，会"收不到 + 发送永远失败"，且不报错。

### 2. 51 的驱动迁到 STM32，只有 4 类要改

| 类别 | 51 写法 | STM32 写法 |
| --- | --- | --- |
| 引脚 | `sbit SCK = P1^0;` `SCK = 1;` | `HAL_GPIO_WritePin(端口, 引脚, 电平)` |
| 类型 | `u8` | `uint8_t` |
| 延时 | `delay_us(10)` | `HAL_Delay` / DWT |
| SPI | 软件翻转引脚 | `HAL_SPI_TransmitReceive`（快 10 倍） |

**不用改**：寄存器地址、命令、位掩码——这些芯片决定，跟 MCU 无关。

### 3. 查手册的"3 分钟法"

```
不知道寄存器地址 → 第 6 节开头那张表（Address / Mnemonic）
不知道某位含义   → 同一张表的 Bit 列
不知道编码表     → 该寄存器的 Description 列（速率/功率/ARD 都在里面）
不确定默认值     → Reset Value 列
不确定能不能写   → Type 列（R / R/W）
```

### 4. 今天的坑（表格）

| # | 现象 | 原因 | 解决 |
| --- | --- | --- | --- |
| 1 | 编译报 `CSN/CE/IRQ` 未定义 | 这些是 51/正点原子的宏，STM32 工程没有 | 换成 `CS_LOW/CE_LOW` 这类自己定义的 HAL 宏 |
| 2 | `WRITE_REG` 未定义 | 头文件里叫 `SI24R1_WRITE_REG` | 统一命名 |
| 3 | 20 个编译错误 | `.c` 从旧例程整段复制，函数名没加 `Int_` 前缀 | 全局替换统一命名 |
| 4 | 清标志清不掉 | 漏了 `0x20` 命令位 | `SI24R1_WRITE_REG + STATUS` |
| 5 | `while(IRQ==1)` 编译不过 | IRQ 引脚没接线 | 改成轮询 STATUS + 超时 |
| 6 | 掩码抄错的风险 | nRF24 与 Si24R1 差一位 | 以手册 P18 为准 |
