# 学习记录 · 感悟与踩坑

这里不是"今天做了啥"的流水账（那是 [开发日志](../开发日志/) 的活），而是**写给三个月后的自己**的复盘材料。

一份好的复盘笔记应该能回答四个问题：

1. **我当时在想什么？** —— 需求是怎么一步步拆成代码的（思路演进）
2. **我用什么数据结构装它？** —— 为什么是结构体 / 枚举 / 数组
3. **控制流是怎么走的？** —— 谁调谁、节奏怎么来的
4. **哪里踩坑、怎么爬出来的？** —— 现象 / 原因 / 解决

## 每日笔记的固定骨架

```markdown
# YYYY-MM-DD · 一句话标题

## 一、今天的思路是怎么长出来的
   第 1 步：先能跑（最笨的写法，贴 3~5 行代码）
   第 2 步：发现哪里不舒服（重复 / 硬编码 / 记不住）
   第 3 步：抽象（结构体 / 枚举 / 函数）
   第 4 步：再抽象（状态机 / 分层）
   —— 这一步最重要，代码的价值在于"为什么这么写"，不在于"写了什么"

## 二、数据结构全景
   结构体长什么样、每个成员为什么存在
   枚举有哪些值、各自含义
   （可以画个简单的文字关系图）

## 三、控制流
   谁调谁、周期多少、状态怎么变
   （表格：状态 → 行为 → 代码 → 实际效果）

## 四、关键代码（带解释）
   贴最小可复现的片段，每段下面 2~3 行说明"为什么这样写"
   不要贴整个文件

## 五、学习感悟
   3~5 条"以前怎么想 → 现在怎么想"
   可以配截图（放在 2_笔记/ 里，用相对路径引进来）

## 六、踩的坑（表格：现象 / 原因 / 解决）
   原因必须写，只写"改好了"等于没写

## 七、下一步
   3 条以内，具体到"改哪个函数"
```

## 三条写作原则

1. **写"为什么"，不写"是什么"**：`HAL_GPIO_WritePin` 怎么用查手册就有，"为什么要封装成结构体"才是你的思考
2. **踩坑必须写原因**：现象 → 原因 → 解决，三段缺一不可
3. **能配图就配图**：手绘的想法、串口输出、CubeMX 配置截图，都可以放进 [2_笔记](../../2_笔记/) 再引用过来（相对路径 `../../2_笔记/日期/文件名.png`）
